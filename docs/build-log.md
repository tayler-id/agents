# Build log

Tayler asked on 2026-10-11 for the whole project to be built and working, with no questions until it is done. This log records each step, the decisions I made on my own, and what verified each one. Decisions you might want to revisit are marked **Revisit**.

## Scope

From `docs/intent/multiplayer.md` and `docs/build-plan.md`. In scope:

1. Phase 1, the shared record: sync and the access proxy, live tokens, the desktop app, and the team-record tools agents use to find each other's work.
2. Phase 2, the factory: tasks, workspaces and artifacts, pipelines as code, a local git forge for issues and pull requests, boxes, and the bug-fix pipeline.
3. Phase 3, refinement: past runs as test sets, scored proposals, approval.
4. The app's remaining core: rooms, agent memory, skills, plugins, routines, templates, and comments on artifacts.

Out of scope, per the intent: separate customer orgs, a phone app, pipeline changes applied without approval, voice, meetings, Slack and email.

## Rules I am holding myself to

- Every step ends in a check that I watch fail before I trust it.
- Nothing is called done until the whole suite passes (`npm run check`, every step's check, not only the newest), and the real running system has been tried: the background API, a real daemon, and the app.
- Nothing goes to an outside service. Issues, pull requests and webhooks use a local git forge in Docker, so the factory can be proven end to end without touching your GitHub.
- No commits. Everything stays in the working tree for you to review. Tayler allowed commits and branches on 2026-10-13.
- The UI is tested every way available: Playwright headless end to end in Chromium, WebKit and Firefox with two teammates at once, the real Electron app through Playwright, screenshots in light and dark at wide and phone widths that I look at against your design rules, an accessibility scan, and the real path in Chrome against the real server.

### Step 3: live tokens (done)

- `@durable-streams/server` runs inside the API process on loopback, with file-backed storage in `~/.agents-app/streams`. The API proxies `/v1/streams/sessions/<id>`: a machine may write its own sessions' streams, and a person may only read streams of sessions they can see.
- The daemon runs Claude with `--include-partial-messages` and appends each text and thinking chunk to the session's stream through an idempotent producer, so a retry never duplicates tokens. Tokens never touch Postgres.
- Secrets in live text: each block is scrubbed as a whole, and the last 160 characters (or the longest known secret plus 16) are held back until more text follows or the block ends. An unfinished private key is held back entirely.
- Verified by `npm run check:step3` (8 checks, real Claude session): a secret split across chunks never leaves the scrubber, two viewers see identical token sequences, the tokens add up to the finished message, tokens reach a viewer before the finished message reaches Postgres, a quoted secret reaches viewers only as `[secret:AGENTS_TEST_SECRET]`, and other teams and people cannot read or write the stream. Four breaks turned every check red. One check was weak at first and was tightened after a break exposed it.
- **Revisit.** The Node stream server is the protocol's reference implementation. The protocol also has a Caddy server plugin built for production. It is enough for one team on a Mac. Live text trails the agent by about 160 characters because of the hold-back.

### Phase 2: the factory (done)

- **Forge.** A local Gitea (`compose.yaml`, `ops/forge-setup.ts`) holds the team's repos, issues and pull requests, so nothing goes to your GitHub. `server/forge.ts` is the only file that talks to it. Machines clone and push through the API's git proxy with their instance tokens, and the forge's tokens stay on the server.
- **Pipelines as code.** Files in the `team/pipelines` repo. A version is git's blob id for the file. A broken version is recorded with its error and never becomes current. The runner (`server/runner.ts`) keeps every run's state in Postgres, one row per try at a stage, so an API restart loses nothing. Agent stages end with a `report_result` tool call read from the record, with one reminder for an agent that forgets. Checks are commands whose exit code decides, so the runner itself confirms the reproduction fails before the fix and passes after. Loops have caps, then a person decides. Runs stop at the pipeline's spend cap. Webhooks (Gitea's, and each pipeline's own, signed) and cron start runs, and a repeated delivery starts one run.
- **The bug-fix pipeline** (`pipelines/bug-fix.ts`): triage with duplicate and already-fixed checks, a failing test, fix or plan, verify, pull request, the shepherd's gate, merge.
- **Boxes** (`box/Dockerfile`, `server/boxes.ts`): claimed per run up to a limit, released after, stopped when idle, restarted with their home volume, and recreated from the image. Containers start only after their claim commits.
- **Decisions I made, to revisit:**

### Phase 3: refinement (done)

An earlier agent made the first nine, up to `bd20b3c`, and was stopped partway through a tenth. The second round finished that one and made the rest. Every fix that changes what the daemon or the API does has a line in `test/step21b.ts`, a check that writes Claude Code's transcripts itself into a temp `CLAUDE_CONFIG_DIR` and runs the real daemon, folders command, API and Electric on them. It needs no Claude and takes about a minute and a half. It has 59 lines. The fixes that only change types were broken at the compiler instead.

- **The first round.** Every `.env` value under a connected folder, the login shell's values and files sent as base64 are scrubbed, and a daemon that can't read the shell sends nothing. A bare `connect` keeps a folder's visibility. What a session writes while its folder is disconnected stays on the Mac. One bad line, transcript or folder stops no other. A transcript that names another folder's session writes nothing into it. A refused post keeps its lines, and posts are sized by their encoded bytes. A transcript cut short or replaced is read again from its start. `connect` stores a folder in its case on disk.
- **A session the API closes is passed over for good.** A Mac clock ahead of the server's made a session closed by a reconnect look newer than the reconnect, so the daemon took it again and the API refused it on every read. This was the edit the earlier agent left unfinished.
- **The Esc notice shows.** It carried `interrupted: true` where the terminal page looks for `subtype: 'interrupted'`.
- **A transcript block is parsed by its type** with a zod union, in place of `as string` casts. A block with a field of the wrong type, such as a tool call with a number for its id, is a notice that keeps the block as written. The number had made the API refuse the whole post, which parked the session.
- **Tool results for paths outside the connected folder stay on the Mac,** as Tayler decided. A call that names a path in `file_path`, `path` or `notebook_path` has its result replaced, in the event and the raw line, by a note. The path is resolved where it points. The list of calls held back is saved with the offset. Not covered are a Bash command's output, other path fields and the input of a call that writes.
- **Fewer swallowed errors.** Taking a session up counted nothing and logged on every read for any failure but the API's. It now fails the read like any other, which parks the transcript after 3.
- **The daemon's API client returns `unknown`.** Each caller parses what it needs. The claim of a command had been cast, so the payloads of the other kinds of command became zod schemas in `shared/types.ts`. A damaged `daemon.json` was read as no file, and is an error that names it.
- **Types.** `server/folders.ts` uses `SessionId` and `PersonId`. The kinds a person writes are one list, `PERSON_KINDS`. `Session` in `server/record.ts` is the schema's two arms, so an agent's `agent_id` is a string again.
- **The home folder, and any folder above it, can't be connected.** `connect` refuses it and the daemon reads none, since the API can't tell where a Mac's home is.
- **Cost.** A transcript is read 64 KB at a time, so a backlog is never held whole and an old transcript costs its first 64 KB, not 1 MiB. A start line not written yet is searched on from where the last read ended. A session's subagents are found in its own folder, not by walking every entry in the daemon's state. The first uuid is looked for as far in as the start line.

### agents-git v1 (not merged)

- **What changed.** `daemon/agents-git/` is a TypeScript CLI that starts, lists, adopts and finishes the git worktrees agents work in, and keeps a ledger of them in `~/.agents-app/worktrees.json`. `docs/what-each-part-does.md` says what each command does. `test/step22.ts` runs every command against a repo it builds in a temp folder.
- **Decisions I made.**
  - It lives in `daemon/`. The compiler and lint cover only the folders `tsconfig.json` lists, and that file, `eslint.config.js` and `ops/` all need Tayler's approval to change. **Revisit** if it should get a top-level folder, which is one line in each of the two files.
  - Worktrees go in `<main checkout>-worktrees/<name>`, named once in `worktrees.ts`, which is `~/Projects/agents-worktrees/<name>` for this repo. Deriving it from the main checkout keeps a home folder out of the code, and keeps the check's worktrees inside its temp folder without a second env var.
  - `done` keeps the last commit at `refs/agents-git/<name>/done`, not at `refs/agents-git/<name>`. Git can't hold a ref and a folder of refs under the same name, and saves go under `refs/agents-git/<name>/`. In a scratch repo git refused with "'refs/agents-git/alpha' exists; cannot create 'refs/agents-git/alpha/save-1'".
  - A name is used once. start refuses a name the ledger has, finished or not, and a name with refs kept under it, so a kept commit is never overwritten.
  - start takes its worktree and branch back when `npm ci` fails, so it leaves either a ready worktree or nothing.
  - prune leaves out worktrees with no new commits. Main has all their commits, but an agent may have just started in one.
  - A lock whose holder process has exited is cleared. Clearing takes a second lock, so two waiters can't both clear it and both take the first.

### agentsctl preview, the app live from its source (2026-10-15)

Tayler asked for a private copy of the app that updates within a couple of seconds when a file under `app/src` is saved, for the people and agents who work on the screens. `bin/agentsctl preview` is that. It starts this checkout's instance if none runs, as `up` does, and serves `app/` from source on Vite's dev server at 127.0.0.1, from port 8200. The page is signed in as the instance's owner, or as the person `--as` names. `app/`, `package.json` and the lockfile are unchanged, and Vite is the 8.3.4 already installed.

- **What a person sees.** One address to open, with the team's agents, a sample repo and a sample task. I tried it in Chromium against a real component. Saving `app/src/Work.tsx` changed the Send button on the task page 74 ms later in one try and 178 ms later in another, and the half-typed reply in the box stayed. A file that exports more than components, such as `App.tsx` with its `go`, reloads the page instead, in about 200 ms. Ctrl+C or SIGTERM ends the command with exit 0, and the instance keeps running until `bin/agentsctl down`.
- **Vite runs in middleware mode, on a server of the command's own.** Vite's own server hangs a handler for SIGTERM and one for the end of stdin on the process, and each closes the server and calls `process.exit()`. A script that used Vite's server and printed a last result 200 ms after SIGTERM exited 143 and never printed it. The command must print its last result and exit 0, so Vite attaches to a server the command makes and listens on. Taking the handlers off afterwards would not last, since Vite puts them back each time it restarts.
- **The proxy is Vite's, with three hooks.** It already carries long reads and WebSocket upgrades, and the app holds up to five reads open. The `bypass` hook runs before each request and upgrade, drops identity headers and refuses other origins. The `headers` option sets the login, and an event on the upgrade replaces its origin. A proxy of my own on `node:http` would have been about 80 lines for what Vite's already does.
- **Other origins are refused here, and the API gets an origin it accepts.** The API opens a screen's WebSocket only for the origins the instance started with, and the preview's port is not one of them. Giving the API another origin alone would let any page open on this Mac act as the owner, which is what the API's check is for. So the preview refuses a WebSocket with no origin or a foreign one, and an HTTP request with a foreign one. A plain request with no origin passes, as the API allows. Vite's CORS answers are off, and its Host check stays on, which refuses a rebound DNS name.

- **What the review found.** A reviewer on another model read 028da99 and ran the branch's server code against a scratch Postgres. - **What changed.**
  - **B1, a box marked asleep took work (f11d702).** `TAKES_WORK` in `server/scheduler.ts` needs `stopped_at is null` for a box, so a turn asked for after the mark waits as `computer_starting` and the box wakes. Sleeping and placing now exclude each other on the box's row. `markAsleep` in `server/boxes.ts` takes the row `for update`, asks again on the locked row whether anything wants the box, and only then writes the mark. Placement reads the box `for key share`. A turn that arrives while the mark is written waits for it, then waits for the box.   - **S1, a stop never reached a waiting turn (cc31493).** `signalSession` in `server/scheduler.ts` is the one writer of stop and interrupt commands, and it cancels the session's waiting turns first, in the same transaction. The runner's stop (a cancelled run, a stage that timed out or was replaced, a pause), a replay's stop, a person's Interrupt and a room's deadline all call it.
  - **S2, a lost machine left its turn (cc31493).** `lostMachine` in `server/framework.ts` also finds a stage's waiting turn, and cancels it when it fails the stage. A message a machine had claimed ends through `moveMessages` as failed, and its turn ends with it. A message no machine took ends through `failUntakenMessage`, new in `server/durability.ts`, which fails the command and its placed turn in one statement, and `TURN_MOVES` allows `placed` to `failed` for it. Any other kind of command fails with an update that leaves messages out.
  - **S3, commands placed together shared one moment (c1ffdd4).** The command insert sets `created_at = clock_timestamp()`.
  - **S4, a turn waiting for a person was marked stuck (c1ffdd4).** `markStuckTurns` leaves out a session in `needs_input` or `needs_approval`, named `WAITING_ON_PERSON` in `shared/lifecycle.ts`.
  - **S5, one unreadable turn blocked the rest (c1ffdd4).** `placeSession` reads the stored prompt with `safeParse`.
